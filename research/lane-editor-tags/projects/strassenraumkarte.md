# Straßenraumkarte Neukölln — lane tags & rendering

Research note for the parking-lanes / OSM lane editor project. Documents how [Straßenraumkarte Neukölln](https://strassenraumkarte.osm-berlin.org/) interprets OSM lane-related tags, where the implementation lives, and what that implies for a future lane editor.

**Last reviewed:** 2026-07-25  
**Primary sources:** [GitHub repo](https://github.com/osmberlin/strassenraumkarte-neukoelln), [micromap blog post (2021-12-31)](https://strassenraumkarte.osm-berlin.org/posts/2021-12-31-micromap-update), [`mapstyle/README.md`](https://github.com/osmberlin/strassenraumkarte-neukoelln/blob/main/mapstyle/README.md), [`mapstyle/post_processing.py`](https://github.com/osmberlin/strassenraumkarte-neukoelln/blob/main/mapstyle/post_processing.py)

---

## 1. Project overview

**Straßenraumkarte Neukölln** (“street-space map”) is an experimental, architecture-plan-style OSM map focused on the spatial subdivision of urban public space in Berlin-Neukölln. It visualises carriageways, cycle infrastructure, pedestrian crossings, street furniture, buildings, land use, and (via a companion workflow) on-street parking.

Lane rendering is **not** done directly from raw OSM ways in QGIS. A large **QGIS/Python post-processing script** (`post_processing.py`, ~340 KB) normalises lane attributes, computes absolute geometry offsets, generates one line feature per lane, clips markings at junctions, and writes GeoJSON consumed by the QGIS style (`strassenraumkarte.qgz`).

The project is explicitly **experimental and locality-bound**:

- Optimised for **high-detail micromapping** in Neukölln, not global scale.
- Requires centimetre-level preprocessing in a **metric CRS** (default EPSG:25833 / UTM zone 33N).
- About **two thirds** of the preprocessing script concerns lane/cycleway geometry (per the 2021 blog post).
- Junction turn-lane rendering remains largely **unsolved**; complex junctions are cut out via `area:highway` polygons.

Related companion: **Parkraumkarte** (parking-space map) shares the site and uses separate parking preprocessing.

- Preprocessed Neukölln parking prototype data moved to [tordans/parkraum.osm-verkehrswende.org/.../project-prototype-neukoelln/scripts](https://github.com/tordans/parkraum.osm-verkehrswende.org/tree/main/project-prototype-neukoelln/scripts) (per `data/README.md`).

### Processing pipeline (lane-relevant steps)

1. **Download** OSM GeoJSON via `download_geojson.py` (bbox + `rootdir` configurable). Key inputs: `highway.geojson`, `area_highway.geojson`, `path.geojson`, `barriers.geojson`.
2. **Optional** run `street_parking.py` → `layer/geojson/parking/street_parking_lines.geojson`.
3. **Run** `post_processing.py` in QGIS Python console with step flags (`proc_lane_markings = 1` etc.).
4. **Open** `strassenraumkarte.qgz`; export tiles or images.

**Outputs relevant to lanes:**

- `layer/geojson/post_processed/marked_lanes.geojson` — one line per lane with derived attributes (`access`, `turn`, `marking:left/right`, `surface:colour`, `width`, …).
- Stop-line layers generated in the same `proc_lane_markings` block.

**Defaults hard-coded in script** (Berlin-oriented):

```python
lane_width_default = 3        # metres, if width:lanes* absent
cycleway_width_default = 1.5  # metres
parking_width_default = 2.2   # metres
crs_to = "EPSG:25833"         # metric CRS for geometry ops
```

## 3. Tags used for lane rendering

Role column:

- **Access** — who may use a lane (derived `access` field: `vehicle`, `bicycle`, `bus`).
- **Physical** — lane presence, width, surface, separation, buffers.
- **Geometry** — where the OSM centreline sits relative to lane stack (`placement*`).

### Counting rules (summary)

| Lane type | Counted in `lanes=`? | How script extends stack |
|-----------|---------------------|---------------------------|
| Car lanes | Yes (primary meaning in Neukölln practice) | Base count |
| Bus / PSV lanes | **Yes** (`lanes:psv` example: `lanes=3` + `lanes:psv=1`) | `access=bus`; “BUS” symbol |
| Side cycle lanes (`cycleway:left/right/both=lane`) | **No** in mapper `lanes`, but script **adds** them | +1 per side; `access=bicycle` |
| Middle cycle lane (`cycleway:lanes=none\|lane\|none`) | **No** in mapper `lanes`, but script **adds** | +1 per `lane` in list |
| Separately mapped `highway=cycleway` | Independent way | Parallel layer, not stacked |

## 4. Preprocessing / rules (beyond raw tags)

These behaviours matter for an editor that must produce Straßenraumkarte-compatible data:

1. **Way inclusion filter** — Only ways with `lane_markings=yes`, any `turn:*`, or `cycleway(:left/right/both)=lane` enter the main lane pipeline (plus segments at traffic signals/stop signs for stop lines).

2. **Absolute placement (`placement_abs`)** — All geometry is computed from a left→right lane index independent of way direction. `getAbsolutePlacement()` resolves `placement:backward` by mirroring indices.

3. **Offset pipeline** — Sum `width:lanes[0..N-1]` from placement anchor → `offset` → `native:offsetline` → `native:arrayoffsetlines` (count = `lanes-1`, initial spacing `lane_width_default`) → per-instance `offset_delta` correction for variable widths and buffers.

4. **Neighbour continuity** — Segments with same `name` + `highway` and angle &lt; 70° linked as before/after for `placement=transition` and dual-carriageway spreading.

5. **Junction cut-out** — `area:highway` polygons with `junction=yes` (or crossing types) subtract lane markings unless `lane_markings:junction=yes` on the way or `lane_markings=yes` on the polygon.

6. **Dual carriageway spreading** — `dual_carriageway=yes` segments connecting to single-carriageway same-name segments trigger vertex offsets at split points so centre lines do not kink around islands.

7. **Marking style derivation** — Solid vs dashed from `change:*`, `overtaking=no`, turn-lane centre boundary, `lane_markings`, and cycle `cw_lane` type.

8. **Output model** — One GeoJSON line per lane (`instance` 0…N-1) with normalised attributes for QGIS symbology; not OSM tags directly.

9. **CRS & scale** — Metric CRS required; latitude scale factor (`1/cos(lat)`) for Web Mercator tile export documented in README (Berlin ≈ 1.62).

## 5. UX implications for a future lane editor

1. **`placement` is first-class UI** — The editor must let mappers set `placement=right_of:N` (and variants) visually, because it anchors the OSM way within the lane stack. Without it, default centre placement will misalign cycle lanes and stop lines.

2. **Lane count ≠ drawable lanes** — UI should distinguish **mapped car/bus lanes** (`lanes`, `lanes:psv`) from **derived total width** (after adding cycle lanes). Editing only `lanes=2` is insufficient when `cycleway:both=lane` adds two more stripes in preprocessing.

3. **Per-lane arrays** — `width:lanes`, `turn:lanes`, `cycleway:lanes`, `bus:lanes`/`psv:lanes`, `change:lanes` are pipe-separated left→right (with forward/backward merge rules). A lane editor should expose these as aligned columns, not isolated key-value fields.

4. **Directionality** — `lanes:forward/backward`, `placement:forward/backward`, and `oneway` interact. Bidirectional editing needs a clear forward/backward visual model matching script merge order (backward reversed + forward).

5. **Bus vs cycle counting** — UX should not treat bus lanes like cycle lanes: bus lanes belong in `lanes` count; cycle lanes usually do not but expand the rendered stack.

6. **Junction workflow** — Preview should show junction cut-out (`area:highway`) and offer `lane_markings:junction=yes` override. Without area polygons, preview will show messy crossing markings (known unsolved problem).

7. **Defaults are regional** — 3 m car / 1.5 m cycle / 2.2 m parking defaults are Berlin-specific; editor should surface them when `width:lanes` incomplete.

8. **Validation targets renderer** — Consistency checks should mirror script rules (e.g. `len(width:lanes) >= lanes`, placement index within stack, `cycleway:lanes` length matches expanded lane count).

9. **Preview fidelity** — Full Straßenraumkarte accuracy requires metric offsets, buffers, dual-carriageway spreading, and junction clipping — substantially more than drawing N equal stripes on the way line.

10. **`bicycle:lanes` / `vehicle:lanes`** — If the editor writes these (common in OSM wiki examples), Straßenraumkarte will **ignore** them unless also mapped via `cycleway:lanes` or side `cycleway:*=lane`. Editor export or validation should either map between schemes or warn.
